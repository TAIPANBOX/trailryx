# Trailryx 1.3.0

A minor release on the 1.0 surface. A sealed root can now be signed by Keyryx,
with a queue that keeps sealing independent of whether Keyryx answers; the ingest
door can take each agent's own token in place of the fleet secret; and the
agent-event reading maps `dlp_shadow` and names more producers' types among the
refused. Both new features are off until they are configured. Nothing is removed
or renamed, and no record, journal, pack or wire format changes.

## What changed since 1.2.1

- **Seals signed through Keyryx, and queued while it is down (#103).** With
  `TRAILRYX_SIGNER=keyryx`, `TRAILRYX_KEYRYX_URL` (an `http://` origin) and
  `TRAILRYX_KEYRYX_CREDENTIAL_FILE` (the consumer credential Keyryx issued),
  `trailryx-node run` and `trailryx-node events` have each sealed store root signed
  with the key Keyryx holds. Keyryx is never on the write path: a root it cannot
  sign is queued on disk beside the data, under `signing/pending/`, the records
  stay sealed, and the node prints how many roots are waiting and why. `run` tries
  again at every seal, and every 30 seconds while a root waits; `events` signs what
  it sealed before it reports. A root signed late is signed under the time it was queued, so the time
  the verifier checks is the time the node first had the root. The signer refuses
  a key set it cannot read, a signature under a key other than the one it read and
  a signature of the wrong size, and a root Keyryx refuses stays queued. The
  signer's debug output never shows its credential. Any other value of
  `TRAILRYX_SIGNER` refuses at start, and leaving it unset keeps the seal exactly
  as it was.
- **Packs carry the signature and the witness's attestations (#103).**
  `trailryx-node read --pack` attaches the Keyryx signature for the root it packs.
  With `TRAILRYX_WITNESS_ATTESTATIONS` naming the folder Keyryx's witness writes
  to, it also attaches each attestation filed for that root and tenant; a file
  whose name and contents disagree about the root is not attached.
  `trailryx-verify` then reports the pack's `root-signature` and an independent
  `witness`. A root still in the queue is packed unsigned, and the node and the
  verifier both say so.
- **Each agent writes as itself at the ingest door (#104).** Opt-in on
  `trailryx-ingest` and `trailryx-node run`, with four flags that go together:
  `--agent-token-issuer`, `--agent-token-audience`, `--agent-token-jwks` and
  `--agent-token-origin`. Each agent then presents the access token vouchryx
  issued it, as `Authorization: DPoP <token>`, with a DPoP proof it signs for that
  request. Both are verified offline against the issuer's key set by the same
  rules tokenfuse and agent-stack-go apply; the estate's shared table of token
  cases is vendored byte for byte, and every agent and relayed case in it gets the
  answer the table states. Every record a request produces is bound to the token's
  `sub`. A span naming any other agent, the deployment's default agent included,
  is refused, the exporter is told in the partial success, and the refusal is
  written down as one record per batch under the caller's own name. A token for an
  agent outside `--trust-domain` is a 403. Startup refuses a door that could not
  do its job: an empty audience or issuer, a key set with no EC P-256 key, with two
  keys sharing a `kid` or with a private member, an origin that is anything but
  `scheme://authority`, and `--token-file` given as well. Without the four flags
  the door is unchanged.
- **A P-256 verifier that depends on nothing (#104).** `trailryx-verify` gains
  ECDSA P-256 with its own SHA-256, held to every Project Wycheproof P-256 SHA-256
  case in the fixed-width form a JWS signature uses, vendored with its licence.
  Nothing in the pack verifier calls it: it is there so the ingest door can check
  ES256 signatures without a cryptography crate. Three fuzz targets are new, the
  P-256 verifier, the agent-token verifier and the key-set reader, and the first two
  must accept nothing but the exact bytes of their corpus. No third-party
  dependency is added anywhere in this release.
- **For adapter authors (#104).** `trailryx-contracts` gains `RequestContext` and
  a provided `AuthProvider::authenticate_request`, whose default calls
  `authenticate` with the `Authorization` field, so a provider written before it
  compiles and behaves unchanged. `trailryx-otlp` gains `OtlpSource::accept_as`,
  the rejection `NotTheCaller`, and a `not_the_caller` count that reaches the
  anomaly record.
- **`dlp_shadow` is mapped, and the unidentified caller is no agent (#101).**
  `dlp_shadow`, the DLP scanner's finding on a prompt the gateway let through, maps
  as a `PolicyDecision` that allowed the call, at `Warning`, the reading
  `taint_shadow` already has. The subject agent-passport reserves for a caller
  that named no agent, `agent://unidentified.invalid/caller`, is refused as naming
  no agent before the trust domain is compared, so it never holds an import's
  cursor the way a foreign domain does. `MAPPER_VERSION` moves from 112 to 113,
  because stored records gain a new mapping.
- **More types refused by name (#103, #105, #106).** agent-conform's
  `chain_restarted` joins `chain_broken` and `chain_unchained` as a verifier's
  finding about a stream (#103). keyryx's seven witness findings,
  `witness_stream_rewritten`, `witness_stream_truncated`, `witness_chain_restarted`,
  `witness_checkpoint_invalid`, `witness_checkpoint_unsigned`,
  `witness_root_missing` and `witness_root_equivocated`, are the same kind of
  finding made by an independent witness, and what the witness vouches for
  reaches the store through the attestations a pack carries instead (#106).
  wardryx's `agent_assertion_refused` is named as a seventh kind of refused event
  (#105): its subject is wardryx's own binding check, it carries no run, and the
  agent it names was chosen by the key that was refused, so recording it would mean
  moving `data` into the subject or inventing a run, which this reader does for no
  type. A refusal writes no record, so none of these moves `MAPPER_VERSION`.
- **The type is read before the trust domain (#105).** A foreign trust domain is
  the one refusal that holds an import's cursor, because the same bytes would map
  under another `--trust-domain`. That holds only for a type this reading maps, so
  a type refused by name is now counted as that under every domain. A bus carrying
  only wardryx's refused lines (`agent_assertion_refused`, and `policy_updated`
  under `wardryx.internal`) no longer holds the cursor or asks the operator to
  change a domain that was right. Mapped types are compared exactly as before.
- **The workspace version and the README's image lines** name 1.3.0 (the 31
  workspace crates in the lock), so `readme-numbers.sh` holds.
- **Documentation (#103, #104).** The README describes the agent-token door and
  the signer's place in `trailryx-node`. `SECURITY.md` states the door's limits.
  `components.json` declares the signer's four environment names, each with why it
  is read, and `COMPATIBILITY.md` lists the signer, the door and the trait method
  as additive.

## Why a minor

Every new surface is additive under `COMPATIBILITY.md`. The signer's four
`TRAILRYX_` names, the door's four flags and the provided trait method are each
listed as additive in `compat/1.0.json`, and `dlp_shadow` is a new agent-event type
the mapper newly accepts, which that file also lists as additive. The frozen
section is unchanged since 1.2.1 and `scripts/compat-surface.sh` holds it, so
nothing frozen is removed or renamed, which rules out a major; something new is
observable, which rules out a patch.

## Upgrading

- **From 1.2.1, nothing to configure.** The signer and the agent-token door are
  both off until configured, and with neither set a node and a door behave as they
  did in 1.2.1. The frozen surface in `COMPATIBILITY.md` is unchanged.
- **Turning on signing.** Keyryx is reached over plain HTTP only: this build links
  no TLS for that hop and refuses an `https://` origin, so Keyryx belongs on the
  private network beside the node, where the consumer credential crosses in clear.
  The first root signed is the shard's current root, which covers every segment
  already sealed, those sealed under 1.2.1 included; `run` queues it on its first
  pass and `events` at the end of its next run. Roots that were current before
  signing was configured are not signed. Keyryx's signing key is not held in a
  validated cryptographic module, so the signer reports itself as not validated.
  For `read --pack` to attach attestations, point `TRAILRYX_WITNESS_ATTESTATIONS`
  at the folder the witness writes to.
- **Turning on the agent-token door.** A door takes one kind of credential: with
  the four flags it refuses `--token-file`, so every exporter writing to it needs
  its own vouchryx token and DPoP proof, and an exporter holding only the fleet
  secret gets a 401 that names the DPoP scheme. Moving a fleet a few agents at a time means running a second
  door for the agents that have tokens. The door's limits are stated in
  `SECURITY.md`: there is no revocation list, so a token is good for its five
  minutes once issued; proofs are single use per process and held in memory, so two
  doors behind one balancer each remember their own and a restart forgets; and
  there is no server nonce.
- **The trail of shadow DLP findings starts at 113.** A `dlp_shadow` line that a
  1.2.x reader met was refused as an unknown type and its cursor moved past it, so
  1.3.0 does not go back for those lines.
- **keyryx's and agent-conform's newest lines still count as an unknown schema.**
  Both producers stamp `taipanbox.dev/agent-event/v1.0`, which this reader does not
  accept yet, so a line from either is counted as an unknown schema before its type
  is read. Naming the types records the decision for when v1.0 is accepted, which
  is a separate change.
- **Rust callers that build against these crates from git.** The crates are not on
  crates.io, and their Rust APIs are not part of the surface `COMPATIBILITY.md`
  freezes, but three changes would stop such a caller compiling: the ingest
  handler's `submit` takes the caller as a third argument, `trailryx-otlp`'s
  `Rejection` gains `NotTheCaller` and is not marked non-exhaustive, and its loss
  counts gain the `not_the_caller` field.
- **The stack launchers** get the signer, the door and the 113 reading by moving
  their pins to `trailryx:v1.3.0` and `trailryx-node:v1.3.0`. This release changes
  no launcher.

## Not proven

- **A running Keyryx.** The signer, the queue and the attestations were tested
  against an in-process fake Keyryx on a loopback port. No root was signed by a
  running Keyryx, and no attestation written by its witness was attached to a pack.
- **A running vouchryx.** The door was tested with the vendored token table and
  with tokens and proofs a separate pure-Python generator signs, checked by
  OpenSSL as well when it is available. No token minted by a running vouchryx was
  presented to a running door.
- **The producers' own buses.** `dlp_shadow`, wardryx's refused lines and keyryx's
  witness findings were tested with constructed envelopes. `trailryx-node events`
  was not run over a bus any of them wrote.
- **Coverage.** CI has no coverage step, so none was measured.
